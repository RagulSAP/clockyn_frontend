4. Database (schema clockyn_dev)

Rules. The database also holds live legacy schemas. Clockyn work happens only in clockyn_dev (and temporary clockyn_dev_test_* schemas that tests create and drop). Do not create or drop databases, and do not touch any other schema.

Check what the migration runner would do (changes nothing)

cd C:\POC\clockyn_backend
.\.venv\Scripts\Activate.ps1
$env:PGSSLMODE = "require"
python migrate.py --all --dry-run

Build or update the schema, and see its status

python migrate.py --all
python migrate.py --status

On an empty schema it builds everything from clockyn_ddl_latest.sql (tables, enum types, indexes, seed rows) and records the migrations. A second run does nothing. It uses DB_SCHEMA from .env. Tables you added by hand at the end of that file (for example the Video Hub tables) are part of it too, so a fresh build already has them.

Make a schema file you can run by hand (DBeaver or psql)

python scripts/render_schema.py --schema your_schema_name --out your_schema.sql

It rewrites every object to your schema name and refuses the legacy and system schema names. Run the output once, on a schema that does not exist yet.

Restricted database user (recommended; run it yourself as the admin user)

CREATE ROLE clockyn_app LOGIN PASSWORD 'choose-a-strong-password';
GRANT CONNECT ON DATABASE your_database TO clockyn_app;
GRANT USAGE, CREATE ON SCHEMA clockyn_dev TO clockyn_app;
GRANT ALL ON ALL TABLES IN SCHEMA clockyn_dev TO clockyn_app;
GRANT ALL ON ALL SEQUENCES IN SCHEMA clockyn_dev TO clockyn_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA clockyn_dev GRANT ALL ON TABLES, SEQUENCES TO clockyn_app;
-- then remove its access to every other schema, for example:
-- REVOKE ALL ON SCHEMA other_schema_1, other_schema_2, public FROM clockyn_app;

Then put clockyn_app in DB_USER / DB_PASSWORD, and change the master password.

AWS Rekognition setup (face matching) AWS console + one command

Staff face registration and every face punch use Rekognition. Without it, use FACE_BACKEND=mock locally. Do this once per environment, in the same AWS region as your database (ap-south-1).

  1. Create the permission policy. IAM, Policies, Create policy, JSON tab, name it ClockynRekognitionApp. Print the exact JSON with your account id by running python scripts/rekognition_setup.py policy in the backend folder, or use this (replace YOUR_ACCOUNT_ID): 
    {
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "ClockynFacesCollection", "Effect": "Allow",
      "Action": ["rekognition:IndexFaces", "rekognition:SearchFacesByImage", "rekognition:DeleteFaces",
                 "rekognition:ListFaces", "rekognition:DescribeCollection"],
      "Resource": "arn:aws:rekognition:ap-south-1:YOUR_ACCOUNT_ID:collection/clockyn-faces-dev" },
    { "Sid": "ClockynDetectFaces", "Effect": "Allow",
      "Action": ["rekognition:DetectFaces"], "Resource": "*" }
  ]
}
  2. Attach it to whoever runs the backend: on AWS, the task role of the Express service (clockynBackendTaskRole, the one that has the S3 and SES permissions); on your PC, the IAM user or role your AWS CLI uses (aws configure).
  3. Create the face collection (once; needs an admin user who may create collections): 
    cd C:\POC\clockyn_backend
.\.venv\Scripts\Activate.ps1
python scripts/rekognition_setup.py create

    Or with the AWS CLI: aws rekognition create-collection --collection-id clockyn-faces-dev --region ap-south-1. Use a separate collection for production, for example clockyn-faces-prod.

  4. Set these in the backend .env (and as environment variables on AWS): FACE_BACKEND=rekognition, REKOGNITION_REGION=ap-south-1, REKOGNITION_COLLECTION_ID=clockyn-faces-dev, REKOGNITION_THRESHOLD=90. The threshold is a match score from 0 to 100; raise it for fewer wrong matches, lower it if real staff are rejected.
  5. Check it works: 
    python scripts/rekognition_setup.py check

    It prints the region, the collection and which permission is missing, if any.

  6. Cost alert. Rekognition bills per image processed (registration, each punch check, each detection) plus a small charge per stored face. Check the current rates on the AWS pricing page, and set a monthly budget with an email alert (Billing, Budgets).
Privacy. Face data is biometric personal data: get staff consent before they register (DPDP Act). The collection stores face vectors, not photos.
Everyone registers fresh. There are no existing users to migrate, so each person registers their face once in the new app.

Deploy the backend with Amazon ECS Express Mode replaces App Runner and hand-built ECS

Express Mode runs the backend container on ECS Fargate and creates the rest for you: an internet-facing Application Load Balancer (shared by up to 25 Express services), the target group, the security group, HTTPS on an address like https://<service-name>.ecs.ap-south-1.on.aws, CPU-based auto scaling, CloudWatch logging, and canary releases with an automatic rollback alarm on 5XX errors. You only provide the container image and IAM roles. Use the same region as your database (ap-south-1) and replace YOUR_ACCOUNT_ID with your 12-digit AWS account number.

Much less to set up than plain ECS. There is no cluster or task definition to write, no load balancer, target group or certificate to build, and no GoDaddy record is needed to get an HTTPS address. Express already does these.
Run exactly ONE task for now. The live chat sockets, the rate limits and a few caches live in the memory of each container. Express adds tasks automatically under load unless you cap it, so the command below sets minTaskCount=1,maxTaskCount=1. During a release the canary briefly runs a second task; that is fine. Raise the cap only after the live updates move to a shared service.
Checked against the AWS docs, not run on your account. The commands follow the Express Mode documentation (create-express-gateway-service, update-express-gateway-service, describe-express-gateway-service). Anything less certain is marked below. You need a recent AWS CLI v2 that has the express-gateway commands.

What you will create (in this order)

  1. ECR repository and the pushed image
  2. IAM roles: execution role, infrastructure role (Express), task role
  3. A secret in Secrets Manager and a log group
  4. The Express service (one command)
  5. Database access and the database tables
  6. Load balancer idle timeout for chat, then the final checks

Step 1: ECR repository and image

  1. AWS Console, Amazon ECR, Repositories, Create repository. Visibility Private, name clockyn-backend, switch on Scan on push.
  2. On your PC (Docker Desktop must be running), in PowerShell: 
    $ACCOUNT = "YOUR_ACCOUNT_ID"
$REGION  = "ap-south-1"
$REPO    = "$ACCOUNT.dkr.ecr.$REGION.amazonaws.com/clockyn-backend"
aws ecr get-login-password --region $REGION | docker login --username AWS --password-stdin "$ACCOUNT.dkr.ecr.$REGION.amazonaws.com"
cd C:\POC\clockyn_backend
docker build --platform linux/amd64 -t clockyn-backend:1 .
docker tag clockyn-backend:1 "${REPO}:1"
docker push "${REPO}:1"

    The first build is slow (many system packages). Use a new tag for every release (:2, :3, ...) so you can roll back. The image must be linux/amd64 (Express defaults to X86_64).

Step 2: IAM roles

Express needs two roles, and the backend itself needs a third (what the running code may do). Create the three roles once. If you already created them for an earlier attempt, skip this block.

@'
{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"ecs-tasks.amazonaws.com"},"Action":"sts:AssumeRole"}]}
'@ | Set-Content trust-tasks.json -Encoding ascii
@'
{"Version":"2012-10-17","Statement":[{"Sid":"AllowAccessInfrastructureForECSExpressServices","Effect":"Allow","Principal":{"Service":"ecs.amazonaws.com"},"Action":"sts:AssumeRole"}]}
'@ | Set-Content trust-infra.json -Encoding ascii

aws iam create-role --role-name ecsTaskExecutionRole --assume-role-policy-document file://trust-tasks.json
aws iam create-role --role-name clockynBackendTaskRole --assume-role-policy-document file://trust-tasks.json
aws iam create-role --role-name ecsInfrastructureRoleForExpressServices --assume-role-policy-document file://trust-infra.json

aws iam attach-role-policy --role-name ecsTaskExecutionRole --policy-arn arn:aws:iam::aws:policy/service-role/AmazonECSTaskExecutionRolePolicy
aws iam attach-role-policy --role-name ecsInfrastructureRoleForExpressServices --policy-arn arn:aws:iam::aws:policy/service-role/AmazonECSInfrastructureRoleforExpressGatewayServices

Then add two inline policies in the console (IAM, Roles, the role, Add permissions, Create inline policy, JSON tab).

Create the service (PowerShell, in the same folder). It runs 1 vCPU and 2 GB, one task, health check on /health:

cd C:\POC\clockyn_backend
aws ecs create-express-gateway-service `
  --service-name clockyn-backend `
  --execution-role-arn arn:aws:iam::YOUR_ACCOUNT_ID:role/ecsTaskExecutionRole `
  --infrastructure-role-arn arn:aws:iam::YOUR_ACCOUNT_ID:role/ecsInfrastructureRoleForExpressServices `
  --task-role-arn arn:aws:iam::YOUR_ACCOUNT_ID:role/clockynBackendTaskRole `
  --primary-container file://primary.json `
  --cpu 1024 --memory 2048 `
  --health-check-path /health `
  --scaling-target "minTaskCount=1,maxTaskCount=1" `
  --region ap-south-1 `
  --monitor-resources

It shows the resources as they are created (press Ctrl+C to stop watching; the service keeps deploying). The first deployment takes several minutes. The output includes the service ARN; keep it, every later command uses it. To find it again, and the address of the service:

aws ecs list-services --cluster default --region ap-south-1
$SVC = "arn:aws:ecs:ap-south-1:YOUR_ACCOUNT_ID:service/default/YOUR-SERVICE-NAME"
aws ecs describe-express-gateway-service --service-arn $SVC --region ap-south-1 --query "service.activeConfigurations[0].ingressPaths[].endpoint"

The address looks like https://clockyn-backend-xxxx.ecs.ap-south-1.on.aws. It is already HTTPS, which is what release builds of the app need. The health check path Express uses by default is /ping; the command above sets /health, which is the backend's real health endpoint.

Step 5: Database access and tables

Let the service reach the database. Express creates its own security group. Read its id, then open your database's security group (EC2, Security Groups) and add one inbound rule: PostgreSQL 5432 from source = that security group. The database must be reachable from the VPC the service uses (Express uses the default VPC and its public subnets unless you pass --network-configuration "subnets=...,securityGroups=...").

aws ecs describe-express-gateway-service --service-arn $SVC --region ap-south-1 --query "service.activeConfigurations[0].networkConfiguration"

Create the tables (one time). The simplest way is from your PC if it can reach the database (section 4 of the first tab: python migrate.py --all). If it cannot, run the migration runner as a one-off task using the service's own task definition:

$d   = aws ecs describe-express-gateway-service --service-arn $SVC --region ap-south-1 | ConvertFrom-Json
$cfg = $d.service.activeConfigurations[0]
@{ containerOverrides = @(@{ name = "Main"; command = @("python","migrate.py","--all") }) } | ConvertTo-Json -Depth 5 | Set-Content overrides.json -Encoding ascii
@{ awsvpcConfiguration = @{ subnets = @($cfg.networkConfiguration.subnets); securityGroups = @($cfg.networkConfiguration.securityGroups); assignPublicIp = "ENABLED" } } | ConvertTo-Json -Depth 5 | Set-Content netcfg.json -Encoding ascii
aws ecs run-task --cluster default --launch-type FARGATE --task-definition $cfg.taskDefinitionArn --network-configuration file://netcfg.json --overrides file://overrides.json --region ap-south-1

Open the task logs (CloudWatch, /ecs/clockyn-backend): you should see done baseline applied (or noop if the schema already exists). Less certain: the container name Main is what Express uses; if the run fails with a container-name error, list the real name with aws ecs describe-task-definition --task-definition $cfg.taskDefinitionArn --query "taskDefinition.containerDefinitions[].name". Use python,migrate.py,--status the same way to see what is applied. The extra tables added by hand at the end of clockyn_ddl_latest.sql (for example the Video Hub tables) are not created by the runner; run those in DBeaver.

Step 6: Chat connections (load balancer idle timeout)

The chat sockets are quiet between messages, and an ALB closes idle connections after 60 seconds by default. Open EC2, Load balancers, select the load balancer Express created for the service (your service in the ECS console links to it), Attributes, Edit, set Idle timeout = 300 seconds, Save. This is an ordinary setting on a load balancer in your account. If chat starts dropping every minute again after a release, check that this value is still 300.

Step 7: Final checks

  1. Open https://YOUR-SERVICE-ADDRESS/health (should say ok) and /ready (ok means the database is reachable).
  2. Open /auth/config. It should show "user_auth": "email".
  3. In the app, set EXPO_PUBLIC_API_BASE_URL=https://YOUR-SERVICE-ADDRESS (section 3 for local testing, the Expo build tab for EAS builds). In the admin web app, set API_BASE in UI_ADMIN_APP\js\config.js to the same address (it may still point at the old App Runner address).
  4. Razorpay webhook: set it up and test it in Step 8 below.

Step 8: Razorpay webhook (the payment safety net)

When someone pays, the app asks the server to verify and activate the plan. If the app is closed or loses its connection right after the payment, only the webhook can still activate the plan, and it is what fills the gen_webhook_events table. Without the secret every webhook is refused, so that table stays empty and nothing warns you, because normal payments still work.

  1. Secret on the server. Add RAZORPAY_WEBHOOK_SECRET to the Secrets Manager secret clockyn/backend (a random string you choose) and keep the line { "name": "RAZORPAY_WEBHOOK_SECRET", "valueFrom": "YOUR_SECRET_ARN:RAZORPAY_WEBHOOK_SECRET::" } in the secrets list of primary.json. Then send the whole file again (the update command under "Releasing a new version later").
  2. Webhook in Razorpay. Razorpay dashboard, Settings, Webhooks, Add New Webhook. Webhook URL https://YOUR-SERVICE-ADDRESS/webhook/razorpay (exactly this path, no trailing slash). Secret: the same value as above. Tick the events payment.captured, order.paid and payment.failed (payment.authorized is optional). Test mode and Live mode have separate webhooks: add it in the mode you are using.
  3. Check the server side without paying (this sends an invalid signature, so it stores nothing): 
    curl.exe -i --ssl-no-revoke -X POST https://YOUR-SERVICE-ADDRESS/webhook/razorpay -H "Content-Type: application/json" -H "X-Razorpay-Signature: test" -d "{}"
    400 "Invalid webhook signature" means the route works and the secret is set (this is the good answer). 503 "Webhook is not configured" means the secret is missing on the server (that is what stops the table filling up).

  5. If Razorpay shows 200 but the table is still empty, or the log shows a database error, check that the table has its unique index (the webhook insert needs it): 
    SELECT indexname FROM pg_indexes WHERE schemaname = 'clockyn_dev' AND tablename = 'gen_webhook_events';
-- expected: gen_webhook_events_pkey and gen_webhook_events_event_id_key. If the second is missing:
CREATE UNIQUE INDEX IF NOT EXISTS gen_webhook_events_event_id_key ON clockyn_dev.gen_webhook_events USING btree (event_id);

Switch on login enforcement security finding S-01 and S-02

Until these are on, the server lets a request through without a login token, and the admin console proves who the operator is only by their e-mail header. Switching them on has three settings, and the order matters. The longer checklist and smoke test are in docs\REQUIRE_AUTH_ROLLOUT.md in the app folder.

SettingWhat it does
REQUIRE_AUTH=1Every route that is not public needs the app's login token (no token: 401). The chat sockets need ?token=. The service refuses to start if AUTH_TOKEN_SECRET is missing or shorter than 32 characters.
OPERATOR_ENFORCE=1The admin console routes need an operator credential (the console's session token or the operator key).
OPERATOR_LEGACY_ADMIN_ID=0Turns off the old "operator e-mail in a header" login. Only the session token and the key work.

Before you start (once)

  • AUTH_TOKEN_SECRET is in Secrets Manager (a random string of 32 or more characters, the same on every task) and in the "secrets" list of primary.json. Do not change it later: that signs everyone out.
  • OPERATOR_API_KEY (24 or more characters) is in the secret and in primary.json. Keep it for scripts only; never put it in the console's JavaScript.
  • Migration 033 (users.auth_epoch) is applied. Take a database snapshot.

The order

  1. Release the new backend with none of the three settings. It accepts both the old and the new operator login, so nothing breaks. In CloudWatch (/ecs/clockyn-backend) you will now see lines that start with SECURITY:; they list what is still switched off.
  2. Publish the updated console (the UI_ADMIN_APP folder) wherever it is hosted, press Ctrl+F5, sign in once with the e-mail code and open a few pages (Organizations, Subscriptions, Live Chat). They should all load.
  3. Publish the new app build and raise the minimum supported version (the /version/check table) so old builds are asked to update. Old builds have no token and would get 401 everywhere after the switch. Let the staff sign in once so every active phone holds a token.
  4. Test on staging first with the three lines and a real phone build (smoke test in docs\REQUIRE_AUTH_ROLLOUT.md).
  5. Production: add these three lines to the "environment" list of primary.json, then send the complete file (the release command above): 
        { "name": "REQUIRE_AUTH", "value": "1" },
    { "name": "OPERATOR_ENFORCE", "value": "1" },
    { "name": "OPERATOR_LEGACY_ADMIN_ID", "value": "0" },
  6. Check: sign in to the app and the console, and open chat and a report. A call without a token must now answer 401: 
    curl.exe -i https://YOUR-SERVICE-ADDRESS/gen-dashboard/organizations
  7. Roll back: remove the three lines and send the file again. Do not change AUTH_TOKEN_SECRET while rolling back.

On your own PC the same three lines go in the backend .env, but leave them off for normal local testing (the local test server and some tests assume they are off).

Good to know

  • Watch or inspect: aws ecs monitor-express-gateway-service --service-arn $SVC and describe-express-gateway-service. Logs are in CloudWatch under /ecs/clockyn-backend.
  • Remove everything: aws ecs delete-express-gateway-service --service-arn $SVC --monitor-resources. The log group and ECR images stay until you delete them.

A push needs three things to line up: the app carries the Firebase file of your project and registers its device token, the backend holds a key of the same project and sends through Google, and the phone allows notifications. If any one is missing, the app keeps working but nothing arrives. Do the steps in this order.

Part A. Firebase project and the Android app (once)

  1. Open the Firebase console and use the project of the app (it is clockyn-aurocloud today). Use one project for the app and the backend; a key from another project makes Google reject every push.
  2. Project settings (gear icon), General, Your apps: there must be an Android app whose package name is exactly com.clockyn.app (the APP_ID of the app). Add it if it is missing.
  3. On that app click google-services.json to download it and put it in C:\POC\clockyn_frontend (it is already committed there, so only replace it if you changed the Firebase app). app.config.ts picks it up by itself; nothing else to edit.
  4. Project settings, Cloud Messaging: Firebase Cloud Messaging API (V1) must say Enabled. If it does not, open the three-dot menu there, Manage API in Google Cloud Console, and click Enable.

Part B. The backend key (once, then after every key change)

  1. Project settings, Service accounts, Generate new private key. A .json file downloads. It is a password for sending pushes as your project: never commit it to git and never send it in chat.
  2. Open the file. You need five values from it:
    Backend settingValue in the JSON file
    FCM_PROJECT_IDproject_id
    FCM_CLIENT_EMAILclient_email
    FCM_PRIVATE_KEY_IDprivate_key_id
    FCM_CLIENT_IDclient_id

Then add them to the "secrets" list of primary.json (Express tab, Step 4), next to the others, and send the complete file again (Express tab, "Releasing a new version later"): 
        { "name": "FCM_PROJECT_ID", "valueFrom": "YOUR_SECRET_ARN:FCM_PROJECT_ID::" },
    { "name": "FCM_CLIENT_EMAIL", "valueFrom": "YOUR_SECRET_ARN:FCM_CLIENT_EMAIL::" },
    { "name": "FCM_PRIVATE_KEY_ID", "valueFrom": "YOUR_SECRET_ARN:FCM_PRIVATE_KEY_ID::" },
    { "name": "FCM_CLIENT_ID", "valueFrom": "YOUR_SECRET_ARN:FCM_CLIENT_ID::" },

Part C. iPhone (only if you ship iOS)

  1. Firebase, Project settings, Your apps: add an iOS app with the bundle id com.clockyn.app and download GoogleService-Info.plist.
  2. Part D. Build the app again and allow notifications

  1. Any change to google-services.json or to the Firebase plugin needs a new native build, not only an update. Build with the cache cleared (Expo build tab, Step 4), for example: 
    eas build --profile preview --platform android --clear-cache
  2. Install the new build. If an older Clockyn is on the phone, uninstall it first.
  3. Open the app and sign in, then tap Allow on the notification question (Android 13 and later ask once; if you tapped Don't allow, turn it on in Android Settings, Apps, Clockyn, Notifications). The app sends its device token to the backend when you sign in and every time it comes to the front.

Part E. Test it

  1. Sign in on the phone as the organization admin, then press the Home button so the app is in the background (a push is shown by the phone only when the app is not open on that screen).
  2. From the admin web app, Live Chat, send the organization a message. A notification should appear within a few seconds. Tapping it opens the chat.
  3. Not arriving? Look in the backend logs (CloudWatch /ecs/clockyn-backend), search [Notify] and [FCM]:
    Log lineMeaning and fix
    [FCM] not configuredPart B is incomplete on the server: a secret is missing from primary.json or misspelled. Fix it and release again.
    [Notify] no push token registered for N user(s)The phone never sent a token: notifications were denied, the build has no google-services.json, or nobody signed in on it. Repeat Part D. You can also look at the table clockyn_dev.user_push_tokens for the admin's user_id.
    [Notify][FCM] status=200Google accepted the push. If the phone still shows nothing, check its notification settings and battery saver for Clockyn.

Google Maps key for Android Google Cloud console + EAS + one app build

The Android app draws its maps (branch picker, staff location, visit trail) with Google Maps, and Google only serves map tiles to an app that carries a valid key. The key is read from the variable GOOGLE_MAPS_API_KEY when the app is built (app.config.ts). iPhones use Apple Maps and the web version uses Leaflet, so neither needs a key. Do the steps in this order.

Why a development build can show the map and a preview build not. Each EAS profile has its own variables (Expo build tab, Step 3) and the local .env file is never uploaded to EAS. A key that exists only in one environment, or only on your PC, is missing from the other builds. Expo Go also ships a key of its own, so it always shows maps. A build without a key shows "Map unavailable: this build has no Google Maps key" instead of a map.

Step 1. Choose the Google Cloud project and billing

  1. Open the Google Cloud console and sign in with the company Google account.
  2. In the project picker at the top, select the project of the app. The Firebase project (clockyn-aurocloud) is also a Google Cloud project, so you can use it and keep everything in one place. Or create a new project (New project) named for example clockyn-maps.
  3. Billing. Google requires a billing account on the project before the Maps SDK works, even though there is a monthly free usage allowance. Open Billing, link or create a billing account (a card is asked once). Check the current free allowance and prices on the Google Maps Platform pricing page before you go live.

Step 2. Turn on the Maps SDK for Android

  1. Open APIs & Services, then Library.
  2. Search Maps SDK for Android, open it and click Enable. (Not "Maps JavaScript API" and not "Maps SDK for iOS".)

Step 3. Create the key

  1. APIs & Services, Credentials, Create credentials, API key. A key that starts with AIza is shown. Copy it and keep it ready (do not send it in chat or commit it to git).
  2. Click Edit API key (or the key's name) and rename it Clockyn Android Maps.
  3. Do not close the page yet: Step 4 restricts the key. An unrestricted key can be copied out of the app and used by anyone, and you pay for their use.

Step 4. Get the signing fingerprint (SHA-1) of the build

Google ties the key to the app by its package name and the SHA-1 fingerprint of the certificate that signed the build. Package name: com.clockyn.app (the APP_ID in app.config.ts). Get the SHA-1 that EAS signs with:

cd C:\POC\clockyn_frontend
eas credentials --platform android
  1. Choose the build profile (preview), then the keystore entry. The screen lists the keystore with its SHA1 Fingerprint, a line of 20 pairs like AB:CD:12:.... Copy it. Less certain: the menu wording changes between EAS versions; the same value is on expo.dev, your project, Credentials, Android, the application identifier, the keystore.
  2. By default EAS uses one keystore for all profiles of the app, so development and preview usually give the same SHA-1. If eas credentials shows a different one for another profile, copy each of them.
  3. No keystore yet? The first Android build asks to generate one (Expo build tab, Step 4). Build once, then come back here.

Step 5. Restrict the key

  1. Back on the key's page, under Application restrictions choose Android apps.
  2. Add an item: Package name com.clockyn.app, SHA-1 certificate fingerprint = the value from Step 4. Add one item per SHA-1 you have (same package name, different fingerprint).
  3. Under API restrictions choose Restrict key and tick only Maps SDK for Android.
  4. Save. The change can take a few minutes to apply.

Step 6. Give the key to the builds

Create the variable in every EAS environment you build (replace PASTE_THE_KEY). The variable is read during the build, so it must exist before you build:

cd C:\POC\clockyn_frontend
eas env:create --name GOOGLE_MAPS_API_KEY --value PASTE_THE_KEY --environment preview --visibility secret
eas env:create --name GOOGLE_MAPS_API_KEY --value PASTE_THE_KEY --environment development --visibility secret
eas env:create --name GOOGLE_MAPS_API_KEY --value PASTE_THE_KEY --environment production --visibility secret

Check that it is there (the value of a secret is hidden, only the name is listed):

eas env:list --environment preview

For builds on your own PC (npx expo run:android), put the key in the app's .env file (it is gitignored) and prebuild again:

GOOGLE_MAPS_API_KEY=PASTE_THE_KEY

Older EAS versions use eas secret:create instead of eas env:create.

Step 7. Build again and test

The key is baked into the app at build time, so an update alone is not enough; build a new APK. Add --clear-cache so the old manifest is not reused:

eas build --profile preview --platform android --clear-cache
  1. Install the new APK (uninstall the old Clockyn first if the phone refuses it).
  2. Sign in and open Staff location (or the branch picker). Map tiles and the markers should appear within a few seconds.
What you seeMeaning and fix
"Map unavailable: this build has no Google Maps key"The variable is missing in the EAS environment of that profile, or you built before adding it. Check eas env:list --environment preview, then build again.
Grey or empty map (maybe the Google logo), markers missingGoogle refused the key. Check, in this order: the Maps SDK for Android is enabled (Step 2); billing is linked (Step 1); the package name is exactly com.clockyn.app and the SHA-1 is that of this build's keystore (Step 5); wait a few minutes after saving. To see Google's reason connect the phone by USB and run adb logcat | findstr /i Authorization, then open the map. Step 8. Before publishing on Google Play

  1. With Play App Signing (the default) Google signs the app you download from the store with a key of its own, so its SHA-1 differs from the EAS keystore. In Play Console open your app, Test and release, Setup, App signing, and copy the SHA-1 of the App signing key certificate.
  2. On the key in Google Cloud (Step 5) add one more item: package com.clockyn.app with that SHA-1. Keep the EAS one as well, so preview builds keep working.

Good to know

  • The key ends up inside the app package, so it can be extracted. That is normal for Android maps keys; the package + SHA-1 restriction and the API restriction (Step 5) are what protect it. Never skip them.
  • Set a budget alert (Billing, Budgets & alerts) so a surprise cost is noticed early.
  • To replace a leaked key: create a new key (Step 3 to 5), update the EAS variable (eas env:update, or delete and create again), build again, then delete the old key in Google Cloud.
  • You do not need a key for the admin web app or for the app's web version; both use Leaflet.

Troubleshooting

SymptomLikely cause and fix
The preview or production app closes the moment it opens (the development build works)Find the cause with adb logcat -b crash -d (phone on USB) or in EAS Observe. Usual causes: google-services.json missing from the build, a variable set in the wrong EAS environment (check with eas env:list --environment preview), or an http:// backend address (release builds block it). After fixing, build again with --clear-cache.
The map (branch picker, staff location) is blank or says "Map unavailable" in a preview or production build, but works in a development buildFollow the Maps key tab. "Map unavailable" means the key was not in that build's EAS environment (eas env:list --environment preview). A grey or empty map means the key is there but Google rejects it: the package name or SHA-1 on the key does not match the build, or "Maps SDK for Android" is not enabled.
Push notifications do not arriveFollow the Push (FCM) tab, step by step. Most often the FCM_* secrets are missing from primary.json on the server, or the phone never registered a token.
The app still talks to the old backendNo .env, or the bundler was not restarted. Set EXPO_PUBLIC_API_BASE_URL and run npx expo start -c.
Phone cannot reach http://192.168.x.x:8080Start the backend with --host 0.0.0.0, allow port 8080 in the Windows firewall, and keep the phone on the same Wi-Fi.
Backend: server closed the connection unexpectedlyThe database instance is unhealthy or unreachable. Check it in the RDS console (status, security group, logs).
Backend: DB_SCHEMA environment variable is requiredSet DB_SCHEMA=clockyn_dev in the backend .env.
Sign-in code never arrives (email mode)SES: the sender must be verified, and while SES is in sandbox mode so must every recipient. Request production access.
Face register/punch: "face recognition is not available" or access deniedThe IAM policy is not attached to the role that runs the backend, or the collection does not exist. Run python scripts/rekognition_setup.py check.
Face punch rejects the right personLower REKOGNITION_THRESHOLD a little (for example 85) and ask them to register again in good light.
Everyone gets "too many requests"Behind a load balancer set TRUST_PROXY=1, otherwise all users share one address for the rate limits.
Photos upload fails on iPhone (HEIC)The app converts to JPEG before upload. Older app builds are accepted by the backend on most upload routes; face routes need JPEG.
Express: create fails with "Unable to assume the service linked role"The new IAM roles have not propagated yet. Wait about a minute and run the command again.
Express: the service address does not openThe first deployment takes several minutes. Watch it with aws ecs monitor-express-gateway-service --service-arn ... until the status is ACTIVE, and check the address with describe-express-gateway-service (Express tab, Step 4).
Express: the task stops right after startingOpen the logs in CloudWatch (/ecs/clockyn-backend). Usual causes: a setting or secret ARN typo in primary.json (check the secrets values), the execution role cannot read the secret, the container cannot reach the database (the database security group must allow the service's security group on 5432), or the image tag does not exist in ECR.
Express: the health check keeps failingThe container must answer /health on port 8080. Express checks /ping unless you set --health-check-path /health, and the container port must be 8080 in primary.json.
Express: "CannotPullContainerError"The execution role is missing AmazonECSTaskExecutionRolePolicy, the image tag is not in ECR, or the image was built for another CPU type. Build with --platform linux/amd64.
After an update, settings or secrets disappearedSend the complete primary.json every time (image, environment and secrets), not just the image.
gen_webhook_events stays emptyRun the curl check in Express tab, Step 8. 503 means RAZORPAY_WEBHOOK_SECRET is not set on the server; 400 for a real Razorpay delivery means the secret in the Razorpay dashboard differs from the server's; no delivery at all means the webhook URL or events are not set in the dashboard (or it is the other mode, Test versus Live).
Chat disconnects every minuteSet the load balancer idle timeout to 300 seconds (Express tab, Step 6) and re-check it after a release.
Live Chat messages only appear after a refreshThe socket is not connected. Check that the backend with /ws/support-ops and /live-chat/* is deployed, the load balancer idle timeout is 300 seconds (Express tab, Step 6), and the console's API_BASE is the current address. The console falls back to checking every 20 seconds while the socket is down.
Live Chat answers 403 or is missing in the appOnly the admin (role 1) of that organization can use it. Managers and staff do not see the Support tab.
Live Chat: "relation live_chat_thread does not exist"The two tables were not created in clockyn_dev yet (Support tab, Live Chat step 1).
The app's FAQ list is empty, or the console says "FAQ is not set up yet"The table was not created in clockyn_dev yet (Support tab, FAQ Hub step 1), or it is created but empty: run FAQ.sql (step 2). The backend log shows one line "faq: the table support_faq does not exist" when the table is missing.
Running FAQ.sql fails with "column faq_bucket does not exist"The table was created from an older version of the block. Run the ALTER TABLE ... ADD COLUMN IF NOT EXISTS faq_bucket line of step 1, then run FAQ.sql again (it is all-or-nothing, so nothing was half loaded).
A FAQ is saved in the console but not in the appCheck its status: only Active FAQs are sent to the app. Pull down on the FAQ screen to refresh it (the app keeps the list for 5 minutes).
Saving a FAQ answers 409 or 403409: a FAQ with the same question already exists (case does not matter). 403: only a super admin can add, edit or delete FAQs; other operators can only read.
No desktop notification in the consolePress Enable notifications on the Live Chat page and allow it in the browser; notifications show only while a console tab is open and not in focus.
Video upload: "Upload to storage failed"The S3 bucket CORS does not allow your site. The origin must match exactly (for local use http://localhost:*) and PUT must be allowed (Video Hub tab, Step 3). Open the page from http://localhost:..., not as a file.
Admin pages show a CORS error or "Failed to load"If CORS_ALLOWED_ORIGINS is set on the backend, add the admin site's exact origin including the port. Also check API_BASE in UI_ADMIN_APP\js\config.js.
Video upload or delete answers "Only role_id=1 admins can perform this action"Only a super admin can manage videos. The operator row needs role_id = 1 and their email filled in.
A video does not open in the appInstall the new development build (it adds the video player). Also check the video is Active and its file exists in S3 under guide_videos/.
EAS build: no project id / wrong projectSet EAS_PROJECT_ID (Step 2 and 3) for the environment you build.
EAS build works but the app cannot reach the backendRelease builds block plain http://. Use the HTTPS address in the EAS environment variable.
Expo Go says the project is incompatibleExpo Go on the stores is SDK 57; this app is SDK 58. Use a development build (Expo build tab).
