Feature folders: `src/features/requests/staff/`, `src/features/expenses/staff/`.

Route files are thin re-exports in `src/app/staff/{requests,expenses}/*` and `src/app/device-change-request.tsx`.

Structure: `utils/requestRules.ts` and `utils/expenseRules.ts` hold every rule as pure functions (date blocking, slot grid, validation order/copy, badge counts, odometer mode, submit sequences). `hooks/useRequestData.ts` / `useExpenseData.ts` hold the `queryOptions` factories (shared by the screens and the hubs' pre-load) and the per-month / per-day queries. Shared pieces: `RequestCalendarCard`, `DateChips`, `TimeSlotSheet`, `SuccessModal`, `HubCard` (requests); `DateNavigator`, `PhotoCapture`, `ExpenseListCard`, `OdometerParts`, `SuccessModal`, `HubCard` (expenses).

Behaviour kept from the specs: hub cards and copy; prefetch-then-navigate with always-navigate fallback (device change opens immediately); leave = today allowed, Sundays / past days / dates with any existing leave (rejected included) not selectable, multi-date across months, Monday-first grid, Approved / Rejected / Pending overlay; permission = single date, 30-min slots (start strictly later than now on today / when no date is picked, end within 6 h and never past 23:30), v1 validation order and copy, `HH:mm` payload, changing the start clears the end; shift change = New / My Requests tabs, form kept across tabs, success -> My Requests after 1.5 s, refresh on focus; device change = dual mode by the `userId` param (login copy + warning card, replace to `routes.staffLogin` after 2 s; in-app -> back); odometer = photo upload BEFORE the start/stop record call, server-computed distance, readings table, start/stop modals; travel / bills = create record, then upload photo, list + rounded total per date, camera only.

## Fixes applied (v1 -> now)

| v1 issue | Fix |
|---|---|
| Month range built with `toISOString()` (IST dropped the last day of the month, and the first day came from the previous month) | `calendarRange()` uses `monthRange()` from `@/lib/datetime` (IST); tested for Oct 2026 (`2026-10-01..2026-10-31`), Feb leap years. Hub pre-load uses the same range. |
| Hub badge rule differed from the home quick action (`status` vs per-date statuses) | One rule `isPendingRequest` (any pending `date_statuses` entry when present, else request status); hub refetches on focus, after pull-to-refresh, and every submit invalidates `queryKeys.requests.all(userId)`. |
| Leave chip from another month could not be removed (chip resolved the day against the displayed month) | Selected dates are `YYYY-MM-DD` strings; each chip removes its own date. List is kept sorted; payload is sorted. |
| Leave error text lost (`e.response.data.detail` on an `Error`) | Mutations go through `useApiMutation` -> `getErrorMessage` (server `detail`/`message` first, fallback "Failed to submit"). Same for every submit. |
| Calendar cache held only the last fetched month; concurrent-fetch guard left a month without statuses (permission) | One react-query entry per month; while a month has no data, picking is ignored and a spinner overlays the grid; a load error shows an inline retry. |
| Permission/leave/shift: UTC date for `shift_change_date`, local-vs-UTC mismatch between chip and payload | All business dates are IST strings; the shift date comes from `DateField` (`minDate` = IST today) and is sent as is. |
| Success timers not cleared on unmount | `useDelayedCall` clears pending timers on unmount. |
| Device change: bottom nav shown to logged-out users, `mobile` param read nowhere, empty ids could be posted, server `detail` ignored | The pre-login route lives outside the staff shell (no tab bar); `mobile` is not used; empty ids -> "Please login again" toast and no request; errors surface the server message; back button works even without history (falls back to the staff login). |
| Date navigation without try/catch left the blocking overlay stuck; double fetch after every date change; next arrow reached the future | Data loads through react-query (skeleton / error state with retry, no manual loading flag); one fetch per date; the next arrow is disabled at IST today and the picker is capped at today (`clampToToday`). |
| Travel / bills: failed photo upload left a silent orphan record; a retry created a duplicate; `expense_id` could be `undefined` | `submitExpenseWithPhoto`: record kept and reported (`photo_failed`), warning banner + "Retry photo upload" re-uploads for the same `expenseId` (no second record); a missing id throws before any upload. |
| Odometer: "Add First Reading" no-op button; "Today's Readings" title on other dates; mode taken from the first reading of the day only; start km of 0 treated as missing; km not validated | Dead button not ported; title is "Readings for {date}" off today; `openReading()` finds any open trip of the date and treats 0 as recorded; km must be a number >= 0 (max 2 decimals) and a stop may not be below the open start. |
| Amounts accepted 0 / negative / `NaN` | `validateMoney`: positive, at most 2 decimals; inline error + toast. |
| Travel/bills downloaded the whole history and filtered client-side | The list call passes `expense_date`; rows are still filtered by date client-side as a safety net. |
| Bills had no camera permission handling | `PhotoCapture` handles `MediaPermissionError` ("Camera permission is required") for all three screens and any other camera failure. |
| Hub caches (`leave_calendar_cache`, `global.org_shifts_cache`, `odo_*`, ...) were unscoped and never invalidated; `request_update_badge`, `clear_expenses_loading`, `odo_cache_date` were dead | Replaced by user-scoped query keys with `prefetchQuery`; dead flags not ported. Pre-load never blocks navigation (4 s cap, failures ignored). |
| Success modal of v1 shift change kept the overlay up until the history reloaded | "Submitting..." overlay clears with the request; history reload happens in the background. |
| Hardcoded `roleId={3}` bottom nav on the screens | The staff area shell decides the chrome; screens do not render a bar. |

## Deferred (v1 behaviour kept, product decision needed)

- Permission is capped at 6 hours and cannot cross midnight; start slots on "no date selected" assume today (as v1).
- Leave: today is selectable; a rejected date cannot be re-requested; no balance / entitlement check; holidays / weekly-offs other than Sunday are not consulted (the calendar API returns only leave/permission rows).
- Shift change: the employee's current shift is not excluded; no Sunday / holiday rule; no duplicate-request check.
- Expenses: the success modals do not auto-dismiss; no approval status is shown to the employee on the lists (the hub footer still says "submitted for manager approval").
- `expense_type` casing: lists send `TRAVEL` / `BILL` (the API module upper-cases), submit sends `travel` / `bill`, exactly as v1.
- Odometer multi-trip per day is allowed (as v1); after a finished trip the form returns to "start".

## Backend needs

| Endpoint | Current | Needed | Impact |
|---|---|---|---|
| `GET /requests/employee/{userId}/{orgId}` | no `date_statuses` for leave / permission; leave has no request-level `status` (derived client-side) | include `date_statuses` (or a trustworthy `status`) | Hub badge for a partly decided multi-date leave is only as accurate as the request-level status |
| `GET /requests/calendar/{userId}/{orgId}` | one row per date (`type`, `status`); holidays / weekly-offs absent | return holiday / weekly-off dates, or a dedicated "blocked dates" endpoint | Employees can still pick a company holiday |
| `POST /requests/device-change/submit` | unauthenticated; ids come from route params | validate that the user/org pair really has a pending device mismatch; rate-limit; reject duplicates | Anyone who knows an id can create requests |
| `POST /requests/{leave,permission,shift-change}/submit` | duplicate dates / one-permission-per-date enforcement unknown | reject duplicates with a clear `detail` | UI only blocks after the calendar has loaded |
| `GET /expenses/travel-bill/expenses` | `expense_date` filter assumed (the API module sends it); server returns max 30 rows | confirm the date filter is honoured | Client filters again, so a missing filter only costs bandwidth |
| `POST /expenses/travel-bill/submit` + `upload-photo` | two calls, photo failure leaves a record without photo | a delete endpoint for an expense without photo, or a single multipart call | A user who leaves the screen after a failed upload leaves a photo-less record |
| `POST /expenses/odometer/upload-photo` then `/start` / `/stop` | photo first; a failing record call leaves an orphan photo | accept the photo with the record call (or tolerate re-upload) | Retries re-upload the photo |
| `POST /expenses/odometer/stop` | `stop_km < start_km` accepted? unknown | validate and return `detail` | Client already blocks the obvious case |

## Deviations from spec

- Company logo in the headers is not shown: the foundation `Screen` header is title-only and there is no cheap logo query for staff (v1 read a GlobalCache). Titles / subtitles are kept.
- Odometer / form titles drop the emojis (rocket / flag / pin) and use icons; the "N km travelled" line is shown without the pin glyph.
- Shift times in the picker and the form are shown as `09:00 AM` (the API module normalises the server's `09:00AM` text); the history shows the server's `requested_shift_timing` verbatim.
- The photo box keeps the camera-only rule on native; on web the browser file chooser opens (with `capture` on phones), as `pickImage` does everywhere.
- Hub pre-load overlay is capped at 4 s and the leave / permission pre-load fetches only the current month (the month key is shared with the screen).
- Selected-date chips and the calendar status cells use short labels (`Appr`, `Rej`, `Pend`) in addition to colour.
- Added client validations not in v1: positive amount (<= 2 decimals), odometer reading numeric >= 0 and stop >= open start (FIX_POLICY item 10).

## Known gaps

- Leaving the travel / bills screen while the "Retry photo upload" banner is showing forgets the pending record (it stays on the server without a photo; see Backend needs).
- No thumbnail upload progress indicator (the shared client supports `onProgress`; not wired).
- Visual QA on device / browser was not performed in this session (unit + smoke tests only); `expo export --platform web` succeeded and all B12 routes are in the bundle.
