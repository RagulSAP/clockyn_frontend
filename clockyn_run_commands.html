4. Database (schema clockyn_dev)

Rules. The database also holds live legacy schemas. Clockyn work happens only in clockyn_dev (and temporary clockyn_dev_test_* schemas that tests create and drop). Do not create or drop databases, and do not touch any other schema.

Check what the migration runner would do (changes nothing)

cd C:\POC\pa_backend\Clockyn
.\.venv\Scripts\Activate.ps1
$env:PGSSLMODE = "require"
python migrate.py --all --dry-run

Build or update the schema, and see its status

python migrate.py --all
python migrate.py --status

On an empty schema it builds everything (72 tables, 3 enum types, indexes, seed rows) and records the migrations. A second run does nothing. It uses DB_SCHEMA from .env.

Make a schema file you can run by hand (DBeaver or psql)

python scripts/render_schema.py --schema your_schema_name --out your_schema.sql

It rewrites every object to your schema name and refuses the legacy and system schema names. Run the output once, on a schema that does not exist yet.

Restricted database user (recommended; run it yourself as the admin user)

CREATE ROLE clockyn_app LOGIN PASSWORD 'choose-a-strong-password';
GRANT CONNECT ON DATABASE your_database TO clockyn_app;
GRANT USAGE, CREATE ON SCHEMA clockyn_dev TO clockyn_app;
GRANT ALL ON ALL TABLES IN SCHEMA clockyn_dev TO clockyn_app;
GRANT ALL ON ALL SEQUENCES IN SCHEMA clockyn_dev TO clockyn_app;
ALTER DEFAULT PRIVILEGES IN SCHEMA clockyn_dev GRANT ALL ON TABLES, SEQUENCES TO clockyn_app;
-- then remove its access to every other schema, for example:
-- REVOKE ALL ON SCHEMA other_schema_1, other_schema_2, public FROM clockyn_app;

Then put clockyn_app in DB_USER / DB_PASSWORD, and change the master password.

AWS Rekognition setup (face matching) AWS console + one command

Staff face registration and every face punch use Rekognition. Without it, use FACE_BACKEND=mock locally. Do this once per environment, in the same AWS region as your database (ap-south-1).

  1. Create the permission policy. IAM, Policies, Create policy, JSON tab, name it ClockynRekognitionApp. Print the exact JSON with your account id by running python scripts/rekognition_setup.py policy in the backend folder, or use this (replace YOUR_ACCOUNT_ID): 
    {
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "ClockynFacesCollection", "Effect": "Allow",
      "Action": ["rekognition:IndexFaces", "rekognition:SearchFacesByImage", "rekognition:DeleteFaces",
                 "rekognition:ListFaces", "rekognition:DescribeCollection"],
      "Resource": "arn:aws:rekognition:ap-south-1:YOUR_ACCOUNT_ID:collection/clockyn-faces-dev" },
    { "Sid": "ClockynDetectFaces", "Effect": "Allow",
      "Action": ["rekognition:DetectFaces"], "Resource": "*" }
  ]
}
  2. Attach it to whoever runs the backend: on AWS, the App Runner instance role or the ECS task role (the one that has the S3 and SES permissions); on your PC, the IAM user or role your AWS CLI uses (aws configure).
  3. Create the face collection (once; needs an admin user who may create collections): 
    cd C:\POC\pa_backend\Clockyn
.\.venv\Scripts\Activate.ps1
python scripts/rekognition_setup.py create

    Or with the AWS CLI: aws rekognition create-collection --collection-id clockyn-faces-dev --region ap-south-1. Use a separate collection for production, for example clockyn-faces-prod.

  4. Set these in the backend .env (and as environment variables on AWS): FACE_BACKEND=rekognition, REKOGNITION_REGION=ap-south-1, REKOGNITION_COLLECTION_ID=clockyn-faces-dev, REKOGNITION_THRESHOLD=90. The threshold is a match score from 0 to 100; raise it for fewer wrong matches, lower it if real staff are rejected.
  5. Check it works: 
    python scripts/rekognition_setup.py check

    It prints the region, the collection and which permission is missing, if any.

  6. Cost alert. Rekognition bills per image processed (registration, each punch check, each detection) plus a small charge per stored face. Check the current rates on the AWS pricing page, and set a monthly budget with an email alert (Billing, Budgets).
Privacy. Face data is biometric personal data: get staff consent before they register (DPDP Act). The collection stores face vectors, not photos.
Everyone registers fresh. There are no existing users to migrate, so each person registers their face once in the new app.

Deploy the backend on AWS ECS (Fargate) with ECR replaces App Runner

Your DNS is at GoDaddy, so wherever the steps mention DNS, you add records in GoDaddy (Steps 6 and 9). You will run the backend as a container on ECS Fargate (no servers to manage), pulled from ECR, behind an Application Load Balancer that gives you the HTTPS address the app needs. Use the same region as your database (ap-south-1). Replace YOUR_ACCOUNT_ID with your 12-digit AWS account number everywhere.

Run exactly ONE task for now. The live chat sockets, the rate limits and a few caches live in the memory of each container. With two or more tasks, a chat event could land on a different container than the person it is for. Keep Desired tasks = 1 until the live updates are moved to a shared service.
Not tested end to end. The Dockerfile has not been built on this PC, so watch the first build and tell me about any error. The steps below are the standard ECS setup for this container.

What you will create (in this order)

  1. ECR repository and the pushed image
  2. Security groups (load balancer, container, database access)
  3. Two IAM roles (execution role, task role)
  4. A secret in Secrets Manager and a log group
  5. ECS cluster, task definition
  6. Load balancer with HTTPS, then the ECS service
  7. Database tables (one-off task), DNS name, and the final checks

Step 1: ECR repository and image

  1. AWS Console, Amazon ECR, Repositories, Create repository. Visibility Private, name clockyn-backend, switch on Scan on push.
  2. On your PC (Docker Desktop must be running), in PowerShell: 
    $ACCOUNT = "YOUR_ACCOUNT_ID"
$REGION  = "ap-south-1"
$REPO    = "$ACCOUNT.dkr.ecr.$REGION.amazonaws.com/clockyn-backend"
aws ecr get-login-password --region $REGION | docker login --username AWS --password-stdin "$ACCOUNT.dkr.ecr.$REGION.amazonaws.com"
cd C:\POC\pa_backend\Clockyn
docker build --platform linux/amd64 -t clockyn-backend:1 .
docker tag clockyn-backend:1 "${REPO}:1"
docker push "${REPO}:1"

    The first build is slow (many system packages). Use a new tag for every release (:2, :3, ...) so you can roll back.

Step 2: Security groups

Console, EC2, Security Groups, Create. Use the same VPC as your database. Create these two:

NameInbound rules
clockyn-alb-sg (load balancer)HTTPS 443 from 0.0.0.0/0 and HTTP 80 from 0.0.0.0/0
clockyn-ecs-sg (the container)Custom TCP 8080 from source = clockyn-alb-sg (not from the internet)

Then open your database's security group and add one inbound rule: PostgreSQL 5432 from source = clockyn-ecs-sg. This lets the container reach the database. (Later you can remove the open-to-everyone rule on the database.)

Step 3: IAM roles

IAM, Roles, Create role, AWS service, use case Elastic Container Service Task. Create two roles:

3a. clockynEcsExecutionRole (lets ECS pull the image, write logs and read your secrets). Attach the managed policy AmazonECSTaskExecutionRolePolicy. After creating it, add an inline policy so it can read secrets:

{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": ["secretsmanager:GetSecretValue"],
      "Resource": "arn:aws:secretsmanager:ap-south-1:YOUR_ACCOUNT_ID:secret:clockyn/*" }
  ]
}

3b. clockynBackendTaskRole (what the running backend is allowed to do). No managed policy; add this inline policy (replace the bucket name and collection name):

{
  "Version": "2012-10-17",
  "Statement": [
    { "Sid": "S3Objects", "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:PutObject", "s3:DeleteObject"],
      "Resource": "arn:aws:s3:::YOUR_BUCKET_NAME/*" },
    { "Sid": "S3List", "Effect": "Allow", "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::YOUR_BUCKET_NAME" },
    { "Sid": "SesSend", "Effect": "Allow",
      "Action": ["ses:SendEmail", "ses:SendRawEmail"], "Resource": "*" },
    { "Sid": "FaceCollection", "Effect": "Allow",
      "Action": ["rekognition:IndexFaces", "rekognition:SearchFacesByImage", "rekognition:DeleteFaces",
                 "rekognition:ListFaces", "rekognition:DescribeCollection"],
      "Resource": "arn:aws:rekognition:ap-south-1:YOUR_ACCOUNT_ID:collection/clockyn-faces-dev" },
    { "Sid": "DetectFaces", "Effect": "Allow", "Action": "rekognition:DetectFaces", "Resource": "*" }
  ]
}

Because the backend runs under this role, you do not put AWS access keys in any setting.

Step 4: Secrets and logs

  1. Secrets Manager, Store a new secret, type Other type of secret, Key/value. Add one row per secret value:
    KeyValue
    DB_PASSWORDthe database password (use the restricted user, not the master)
    AUTH_TOKEN_SECRETa random string of 32+ characters
    OPERATOR_API_KEYa random string
    RAZORPAY_WEBHOOK_SECRETfrom your Razorpay dashboard
    FCM_PRIVATE_KEY (and the other FCM_* if you use push)from the Firebase service-account file
    Name the secret clockyn/backend. Copy its ARN from the secret page (it ends with a random 6-character suffix).
  2. CloudWatch, Log groups, Create log group /ecs/clockyn-backend, retention 30 days.

Step 5: ECS cluster and task definition

  2. ECS, Task definitions, Create new task definition with JSON. Paste this and edit the values in capitals (account id, secret ARN, image tag, your settings). It runs 1 vCPU and 2 GB:

  "executionRoleArn": "arn:aws:iam::YOUR_ACCOUNT_ID:role/clockynEcsExecutionRole",
  "taskRoleArn": "arn:aws:iam::YOUR_ACCOUNT_ID:role/clockynBackendTaskRole",
  "containerDefinitions": [
    {
      "name": "clockyn-backend",

Add the other settings from the backend .env the same way (for example SELLER_NAME, SELLER_GSTIN, SUPPORT_EMAIL, ANDROID_STORE_URL, IOS_STORE_URL, CORS_ALLOWED_ORIGINS). In the secret reference, the format is SECRET_ARN:KEY::.

Do NOT add OTP_BYPASS, REQUIRE_AUTH, or any AWS access key. Leave REQUIRE_AUTH out until the app has been tested end to end.

Step 6: Load balancer with HTTPS

  1. Certificate (DNS at GoDaddy): AWS Certificate Manager (same region as the load balancer, ap-south-1), Request, public certificate, domain name api.your-domain.com (use a subdomain like api), validation method DNS validation, Request. Then:
    1. Open the certificate. Under Domains you see a CNAME name and a CNAME value. Keep this tab open.
    2. In a new tab, open GoDaddy, My Products, your domain, DNS, Add New Record. Type CNAME.
    3. Name: paste the CNAME name without your domain at the end. ACM shows _a1b2c3.api.your-domain.com.; enter only _a1b2c3.api.
    4. Value: paste the CNAME value, for example _x9y8z7.acm-validations.aws. (if GoDaddy rejects the final dot, remove it). TTL: 600 seconds or the lowest offered. Save.
    5. Back in ACM, wait until the status changes to Issued. It usually takes 5 to 30 minutes after the record is saved. Leave the validation record in place: ACM uses it to renew the certificate automatically.

    The app's release builds need HTTPS, so this step is required. If your domain has CAA records in GoDaddy, one of them must allow amazon.com.

  2. Target group: EC2, Target groups, Create. Type IP addresses, protocol HTTP, port 8080, your VPC. Health check path /health, success code 200. Do not register targets; ECS does that. Name it clockyn-backend-tg.
  3. Load balancer: EC2, Load balancers, Create, Application Load Balancer, name clockyn-alb, Internet-facing, your VPC, two public subnets in different zones, security group clockyn-alb-sg.
    • Listener HTTPS 443: forward to clockyn-backend-tg, using the certificate from above.
    • Listener HTTP 80: redirect to HTTPS 443.
  4. Chat connections: open the load balancer, Attributes, Edit, set Idle timeout = 300 seconds (the chat sockets are quiet between messages; the default 60 seconds would drop them).

Step 7: ECS service

  1. ECS, Clusters, clockyn, Services, Create. Compute: Launch type = Fargate. Task definition: clockyn-backend, latest revision.
  2. Desired tasks = 1.
  3. Networking: your VPC, the public subnets, security group clockyn-ecs-sg, Public IP = ON (this lets the container reach ECR, S3, SES and Rekognition without a paid NAT gateway; the security group still blocks everything from the internet except the load balancer).
  4. Load balancing: Application Load Balancer, use the existing clockyn-alb, container clockyn-backend 8080, listener 443, target group clockyn-backend-tg. Health check grace period 120 seconds.
  5. Create. Wait until the task shows Running and the target group shows healthy. If the task keeps stopping, open the task, Logs tab, and read the error (the usual causes are a wrong setting, no database access, or a secret ARN typo).

Step 8: Create the database tables (one time)

The tables are built by the migration runner. Run it once as a one-off task:

  1. ECS, Task definitions, clockyn-backend, Deploy, Run task. Cluster clockyn, Fargate, same subnets and clockyn-ecs-sg, public IP ON.
  2. Under Container overrides, command override: python,migrate.py,--all
  3. Run, then open the task logs. You should see done baseline applied (or noop if the schema already exists). It writes only into the schema named in DB_SCHEMA.

Do the same with python,migrate.py,--status any time you want to see what is applied. For every later release that has new migrations, run migrate.py --all again before switching the service to the new image.

Step 9: DNS name and the final checks

  1. GoDaddy DNS: in EC2, Load balancers, open clockyn-alb and copy its DNS name (like clockyn-alb-123456789.ap-south-1.elb.amazonaws.com). In GoDaddy, your domain, DNS, Add New Record: type CNAME, Name = api, Value = the load balancer DNS name (without http://), TTL 600 seconds, Save. Use the load balancer name, never an IP address: the load balancer's addresses change. GoDaddy cannot point the bare domain (your-domain.com) at a load balancer, which is why the API uses the api subdomain. Wait a few minutes for it to spread.
  2. Check it resolves first (PowerShell): nslookup api.your-domain.com should show the load balancer. Then open https://api.your-domain.com/health (should say ok) and https://api.your-domain.com/ready (ok means the database is reachable).
  3. Open https://api.your-domain.com/auth/config. It should show "user_auth": "email".
  4. In the app, set EXPO_PUBLIC_API_BASE_URL=https://api.your-domain.com (section 3 for local testing, the Expo build tab for EAS builds).

Releasing a new version later

cd C:\POC\pa_backend\Clockyn
docker build --platform linux/amd64 -t clockyn-backend:2 .
docker tag clockyn-backend:2 "${REPO}:2"
docker push "${REPO}:2"
  1. If this release has new migrations, run the one-off task (Step 8) first.
  2. ECS, Task definitions, clockyn-backend, open the latest revision, Create new revision, change the image tag to :2, Create.
  3. ECS, the service, Update, choose the new revision, Update. ECS starts the new task, waits for it to be healthy, then stops the old one.
  4. Roll back: update the service to the previous task definition revision.

Good to know

  • Cost: you pay for the running task, the load balancer (hourly), logs, and ECR storage. There is no NAT gateway in this setup.
  • Webhook: point the Razorpay webhook to https://api.your-domain.com/webhook/razorpay and use the same secret as RAZORPAY_WEBHOOK_SECRET.
  • Later, scaling: more than one task needs the live chat updates moved to a shared service first. Ask me when you reach that point.

Build the app with Expo (EAS)

You will log in to Expo and build there. These are the steps for this project (eas.json has the profiles development, development-simulator, preview and production).

Before you start

  • An Expo account.
  • Android: nothing else for test builds (EAS creates the signing key). To publish on Google Play you need a Play Console account.
  • iOS: an Apple Developer account (paid) is required for any build you install on a phone.
  • The backend must be reachable over HTTPS from a phone. Release builds block plain http://, and localhost never works on a phone.
  • Firebase (for push): an Android app and an iOS app with the same id as the app (default com.clockyn.app), and the two files google-services.json and GoogleService-Info.plist. For iOS also upload an APNs key in Firebase.

Step 1: install the EAS tool and log in

npm install -g eas-cli
eas login
eas whoami

Step 2: link the app to an Expo project (first time only)

cd C:\POC\pa_frontend\Clockyn
eas init

This creates the project on Expo and prints its project id. The app reads that id from the variable EAS_PROJECT_ID (see app.config.ts), so add it in Step 3 and also set it in your terminal: $env:EAS_PROJECT_ID = "the-id". If eas init asks to edit the app config, let it point to that variable and not hard-code the id.

Step 3: set the build variables on Expo

The local .env file is not uploaded to EAS. Each profile uses the matching EAS environment (development, preview, production). Create the variables for each environment you will build:

eas env:create --name EXPO_PUBLIC_API_BASE_URL --value https://your-backend-address --environment production --visibility plaintext
eas env:create --name EAS_PROJECT_ID --value your-project-id --environment production --visibility plaintext
eas env:create --name EXPO_PUBLIC_SUPPORT_EMAIL --value support@your-domain.com --environment production --visibility plaintext
eas env:create --name EXPO_PUBLIC_ANDROID_STORE_URL --value your-play-store-link --environment production --visibility plaintext

Repeat with --environment preview and --environment development if you build those profiles. Older EAS versions use eas secret:create instead of eas env:create. You can also add them on expo.dev under your project, Environment variables.

For push, upload the Firebase files as file variables (they are not in git):

For Android maps add GOOGLE_MAPS_API_KEY the same way. Skip any of these you are not using yet; the app still builds without push or maps.

Before submitting, make sure the privacy policy link (EXPO_PUBLIC_PRIVACY_POLICY_URL) and the account-deletion information page are set.

Before a real release, check

  • The backend is deployed on AWS with its environment variables set (database, SES sender, TRUST_PROXY=1, AUTH_TOKEN_SECRET, RAZORPAY_WEBHOOK_SECRET) and the IAM role attached.
  • EXPO_PUBLIC_API_BASE_URL is the HTTPS address of that backend, in the same EAS environment you build.
  • Both the app version (version in app.config.ts) and the Firebase apps match the app id.
  • You have tried face punch, photo upload and sign-in on a real Android phone and a real iPhone.

Troubleshooting

SymptomLikely cause and fix
The app still talks to the old backendNo .env, or the bundler was not restarted. Set EXPO_PUBLIC_API_BASE_URL and run npx expo start -c.
Phone cannot reach http://192.168.x.x:8080Start the backend with --host 0.0.0.0, allow port 8080 in the Windows firewall, and keep the phone on the same Wi-Fi.
Backend: server closed the connection unexpectedlyThe database instance is unhealthy or unreachable. Check it in the RDS console (status, security group, logs).
Backend: DB_SCHEMA environment variable is requiredSet DB_SCHEMA=clockyn_dev in the backend .env.
Sign-in code never arrives (email mode)SES: the sender must be verified, and while SES is in sandbox mode so must every recipient. Request production access.
Face register/punch: "face recognition is not available" or access deniedThe IAM policy is not attached to the role that runs the backend, or the collection does not exist. Run python scripts/rekognition_setup.py check.
Face punch rejects the right personLower REKOGNITION_THRESHOLD a little (for example 85) and ask them to register again in good light.
Everyone gets "too many requests"Behind a load balancer set TRUST_PROXY=1, otherwise all users share one address for the rate limits.
Photos upload fails on iPhone (HEIC)The app converts to JPEG before upload. Older app builds are accepted by the backend on most upload routes; face routes need JPEG.
Certificate stays "Pending validation" in ACMThe GoDaddy CNAME is wrong. The Name must not repeat your domain (_a1b2c3.api, not _a1b2c3.api.your-domain.com), and the value must match exactly. Check with nslookup -type=CNAME _a1b2c3.api.your-domain.com.
api.your-domain.com does not openThe GoDaddy CNAME api must point to the load balancer DNS name, and the HTTPS listener needs the issued certificate. DNS changes can take up to an hour with a long TTL. Test with nslookup api.your-domain.com.
ECS task stops right after startingOpen the task, Logs tab. Usual causes: a setting or secret name typo (check the secrets ARNs), the container cannot reach the database (database security group must allow clockyn-ecs-sg on 5432), or the image tag does not exist in ECR.
ECS: target group stays unhealthyThe container must answer /health on port 8080 and clockyn-ecs-sg must allow 8080 from clockyn-alb-sg. Give the service a health check grace period of 120 seconds.
ECS: "CannotPullContainerError"The execution role is missing AmazonECSTaskExecutionRolePolicy, or the task has no route to ECR: turn Public IP ON in the service networking (public subnets) or add a NAT gateway / VPC endpoints.
Chat disconnects every minuteSet the load balancer idle timeout to 300 seconds (Step 6).
EAS build: no project id / wrong projectSet EAS_PROJECT_ID (Step 2 and 3) for the environment you build.
EAS build works but the app cannot reach the backendRelease builds block plain http://. Use the HTTPS address in the EAS environment variable.
Expo Go says the project is incompatibleExpo Go on the stores is SDK 57; this app is SDK 58. Use a development build (Expo build tab).
