# B10 - CRM (hub, View / Assign Leads, Enter / Edit Lead, staff My Leads, CRM badge)

Feature folder `src/features/crm/`. Specs: `pages/09_crm/{crm,assign_leads,enter_leads,emp_crm}.md`.

## Implemented
| Screen | Route | Files |
|---|---|---|
| Admin CRM hub (menu cards, Work Status Overview with day chips + status cells + lead-wise list + lead details sheet, Carry Forward Requests inbox with approve/reject) | `/admin/crm` (tab root) | `src/app/admin/(tabs)/crm.tsx` -> `screens/AdminCrmScreen` |
| View / Assign Leads (day chips + calendar, lead cards, edit / delete / assign / reassign, assign view with branch / department filters) | `/admin/crm/leads` (param `leadId?` opens the assign view) | `src/app/admin/crm/leads/index.tsx` -> `screens/AssignLeadsScreen` |
| Enter / Edit Lead (client fields, category add / delete / search, customer-required date) | `/admin/crm/leads/edit` (param `leadId?` = edit) | `src/app/admin/crm/leads/edit.tsx` -> `screens/EnterLeadScreen` |
| Staff / manager My Leads (status chips, work-status picker, carry-forward request, Add Lead sheet) | `/staff/crm` (tab root) | `src/app/staff/(tabs)/crm.tsx` -> `screens/StaffCrmScreen` |
| CRM tab badge (unseen leads, roles 2/3) | - | `seenLeads.ts` (`crmSeen` service), `hooks/useCrmBadgeSync.ts`, mounted in `Bootstrap` |

Structure: `utils/` (pure logic: `workStatus`, `carryForward`, `leads`, `dates`, `employeeLeads`, `leadForm`, `categories`), `hooks/` (react-query reads/mutations, scoped keys `queryKeys.leads.*`), `components/` (`hub/`, `assign/`, `staff/`, shared `DatePickerModal`, `DateChipBar`, `LeadForm`, `CategoryPicker`, `SuccessPopup`, `StatusBadge`, `PlanBlockedCard`). Layouts: phone single column; tablet 2-column cards; desktop >= 1100 shows overview + carry-forward inbox side by side and the assign view as lead details | employee list columns.

Plan gating: the shell gates the CRM tab. Screens only add what the specs show: hub -> "CRM Unavailable" card with Renew Plan (View Plan Status on iOS) -> billing; staff -> lock card ("contact your admin", no purchase action). Both fail open while the plan is loading/unknown and do not fetch while blocked. View/Assign and Enter/Edit have no client gate: the backend's 403 (wrapped in a 500) is shown through `getErrorMessage` as an error state (lists) or a toast (saves).

## Fixes applied (v1 -> now)
| v1 defect | Fix |
|---|---|
| Edit lead blanked the required date (`requiredDate` vs `createdDate` mapping; save sent `required_date:null`) | Edit passes only `leadId`; the form is prefilled from the cached lead (`leadToFormValues` keeps `requiredDate`) and `toUpdateInput` always sends it explicitly (tests: round-trip, explicit clear -> null) |
| Multi-assignee leads rendered duplicate cards / duplicate keys | `dedupeLeads` merges rows per lead id (assignee names joined) before anything renders |
| Calendar mode never reset after the CF forward-date picker (Add Lead "Required Date" wrote the forward date) | No shared calendar: every picker is its own `DatePickerModal` instance with its own state; forward date also cleared when the dialog closes |
| "Assigned today" client filter hid leads assigned on earlier days | Not applied - the server already returns only today / undated leads; status chips are the only client filter |
| Dead request box / `cfForToday` / `handleSendRequest` (+ `POST /api/leads/{id}/request`), `showSavedPop`, `menuOpenId`, `cfSent`, `filterDate`, unused calendar modes, `leads_success_message`, `clear_crm_loading`, `crm_badge_count`, `emp_home_loading`, `cached_leads` list cache, `leads_need_refresh` flag | Not ported (query invalidation replaces the flags) |
| Silent failures everywhere (status update, CFR, approve/reject, category add, assign, load) | Every mutation toasts the server message (`useApiMutation`); lists show `ErrorState` + retry; no stuck spinners |
| Admin CRM hub spinner forever without auth data; plan-status failure on staff left a permanent spinner | Reactive session/`useOrgPlan` (fails open for both roles) |
| CFRs fetched twice on hub load | One cached `carryForward` query shared by hub / assign / edit |
| `cfrMap` last-write-wins attached the OLDEST CFR | `indexCarryForward`: pending always wins, otherwise the newest approved (tests) |
| Unassigned vs `carry_forward` count/list disagreement | One `bucketOf()` drives counts and filtered list; unknown status counts as pending |
| Unguarded `JSON.parse` of `directLead` / `leadData` route params; JSON blobs in params | ids only (`leadId`); lead read from the query cache |
| Assign/reassign decided by assignee NAME (a failed user join would POST a duplicate assignment) | Decided by `assignedUserId` |
| Branch / department selections persisted from the previous lead; mixed number/string ids; employee-list race with the unfiltered preload | Reset on every open; ids are strings; one server-filtered query keyed by branch + department |
| Hardware back left the assign view's screen; timers not cleared on unmount | `BackHandler` returns to the list first; `SuccessPopup` clears its timer |
| Cached list hidden behind "Loading leads..." | Query cache shows immediately; skeleton only on first load |
| Refetch-after-save inside the save `try` (could report a saved lead as failed) | Save is only the write; the refresh is an invalidation |
| Mobile accepted letters; values untrimmed | Digits only (max 10) and trimmed payloads; validation order/messages unchanged |
| Category: delete without confirmation, stale selection after delete, new category not selected | Delete asks to confirm and clears the field if it was selected; a new category is auto-selected |
| Date format differed per screen (`yyyy / mm / dd` vs `dd / mm / yyyy`) and used device-local / UTC days | All dates via `@/lib/datetime` (IST): `dd MMM yyyy` everywhere; "today / tomorrow / yesterday", lead creation day and CFR submitted day are IST |
| Employee carry-forward invisible after refresh (server never persists `carry_forward`) | The violet "Carry Forward Requested" card is driven by the employee's own pending CFR (`/carry-forward/my`), refreshed after submit; the status control is hidden on it so a duplicate cannot be raised |
| Employee-created leads vanished silently (they are unassigned) | Confirmation toast says the lead was sent to the admin for assignment |
| Absolute-positioned dropdown with a -1000 touch-target hack | `WorkStatusSheet` (bottom sheet on phones, dialog on wide web) |
| Mojibake fallback glyph / logo tile | Not ported; header uses the standard `ScreenHeader` with the org name |
| Badge: computed once per launch, never refreshed | `useCrmBadgeSync` (query-backed, 5-minute refresh while foregrounded; badge cleared + seen list written when the tab is opened) |

## Deferred / Backend needs
Kept as v1 (product / backend decision needed):
- **Carry-forward persistence**: raising a CFR does not set the assignment status to `carry_forward`, so the admin "Carry Fwd" count/filter is effectively 0 (cells and filters work if data ever carries the status). No change to the lifecycle: approve = lead date moves to the forward date + the employee's assignment is deleted; reject = status only; the approved CFR stays in the list forever so a re-assigned lead keeps its "CFR Assigned" marker.
- Reject has no confirmation and no success toast (v1); approve confirms and toasts "CFR approved successfully".
- The CFR list filter compares the SUBMITTED day (not the requested-for day), as v1.
- Server-side visibility rule for employees (`created_date = today OR NULL`, NULL = always eligible); the employee list therefore cannot show future-dated carried-forward leads until their date.
- Admin edit/delete/assign lock for completed leads; employees can still move completed -> pending (no lock), as v1.
- Plan matrix and who may use CRM (manager `Leads Management` permission is checked by the staff Settings shortcut, not here).

| Endpoint | Current | Needed | Impact |
|---|---|---|---|
| `POST /api/leads/carry-forward/request` | Does not change the assignment status | Persist `carry_forward` (restore on reject) or expose a `has_pending_cfr` flag | Admin "Carry Fwd" count; employee list would no longer need the separate `/carry-forward/my` join |
| `GET /api/leads/{org}` | `SELECT DISTINCT` returns one row per (lead x assignment) | One row per lead (aggregate assignees) | Client now merges duplicates; the primary row's status is used |
| `PUT /api/leads/assignment/{id}` | Updates ALL assignment rows of the lead | Update one assignment / reject multi-assignee data | Multi-assignee leads collapse to one user |
| `POST /api/leads/assign` | No duplicate guard; `branch_id` typed int while v1 sent `""` | Upsert; accept empty branch | Client sends `branch_id`/`dept_id` only when the employee has them |
| `POST/GET leads` plan gate | 403 wrapped in a 500 with `detail` | Real 403 | Client already unwraps `"403: msg"` via `getErrorMessage` |
| `DELETE /api/leads/{id}`, `DELETE /api/leads/categories/{id}` | Cascade to assignments / CFRs and behaviour for leads referencing a category unverified | Document / enforce cascade | Orphan CFRs, categories |
| `leads_info.created_date` | Holds the customer REQUIRED date (NULL = no date) | Rename / migrate when convenient | Naming only; semantics preserved |

## Deviations from spec
- Required / forward / lead dates are shown as `dd MMM yyyy` on every screen (specs mix `yyyy / mm / dd` and `dd / mm / yyyy`).
- Staff "no match for the status chip" empty state reads "No Leads Found / No leads match the selected status." (v1: "No Leads on This Date", which was wrong now that no date filter is applied). "No Leads Assigned / Admin hasn't assigned any leads to you yet. Pull down to refresh." is unchanged.
- Picking the status an employee lead already has is a no-op (v1 re-sent the PUT, only useful for bumping `updated_at` for the removed today filter).
- Hub / assign empty states: hub shows a compact "No leads here" / "No requests" message where v1 showed nothing; the CFR tab is shown when any lead or CFR exists (as v1) and empty states appear inside it.
- Staff "Add Category": a small dialog (same as the admin one) instead of the inline input; staff still cannot delete categories.
- Admin Lead Details sheet shows an "Unassigned" pill for unassigned leads (v1 showed the work status).
- Approve confirmation uses the shared confirm dialog with the requested-for date in the message instead of a custom modal with a date chip.
- Hub header shows the org name + "CRM & To-Do" (no logo; logos are not fetched by the new shell). View/Assign and Enter/Edit use the standard back header; list back = `backOr(/admin/crm)`.

## Known gaps
- Android hardware back while the Enter Lead form has unsaved changes is not intercepted (v1 had no prompt either).
- No push/socket-driven CRM badge update (the global socket does not carry lead events); it refreshes every 5 minutes while the app is active and when the staff tab is opened.
- `npm run check:routes` lists only the pre-existing `src/app/dev/ui-kit.tsx` as unregistered (not mine).
